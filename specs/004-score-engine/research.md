# Phase 0 Research: Score Engine

The stack itself is already decided (`architecture/03-technology-stack.md`); this
resolves the choices specific to implementing M6 for real for the first time, including
two schema-level questions the existing docs answer precisely once cross-referenced,
but don't state in one place.

## Decision: `findings.state` is set by the scoring engine, not the fixture

**Decision**: `findings.state` (`open`/`resolved`/`open_overdue`) starts `NULL` and is
written by `RecomputeScoreUseCase` on every run — the fixture
(`demo/fixtures/score-engine-findings.json`) does **not** pre-populate it. Derivation
rule:

- `finding_type = broken_response_promise` or `commitment_met` (the two types tied to a
  `first_response` commitment's lifecycle): state mirrors the `response_pairs.state`
  row reached by joining `findings.cited_event_ids` back to `response_pairs.client_
  event_id` (feature 003's ledger tables) — literally the same three-value enum,
  matching `data-base/03-schema-ledger.md`'s `response_pairs.state` exactly (not a
  coincidence: REQ-M6-09/10/11 quote the same three states).
- Every other seeded `finding_type` (`tone_deterioration`, `recurring_issue`,
  `usage_deviation`, `escalation_language`, `contact_absence`, `relationship_change`,
  `csat_deviation`): always `open`, permanently — these are point-in-time observations
  with no natural "resolved" event in this feature's scope (no reader exists yet to
  ever mark one resolved). `recency = 1.0` for all of them, unconditionally.

**Rationale**: `data-base/05-schema-reasoning.md`'s `findings` table prose states
`state` is "Set once scored (REQ-M6-09/10/11)" — a scoring-engine responsibility, not
reader or fixture data — confirmed by the DDL's grant structure
(`data-base/10-ddl-appendix.md`: `findings` is "append-only except its own lifecycle
columns," with `GRANT UPDATE (status, state) ON findings` specifically called out,
`status` for the future validation gate, `state` for this feature). The derivation
rule itself is inferred from `examples/01` §9's worked numbers: 8 of the 9 findings
show `recency = 1.0` (including `fnd-9`, the resolved-ticket positive finding, whose
half-life formula evaluates to exactly 1.0 at `days_since_resolved = 0` — not a
special case, the same formula everyone else uses just yields 1.0 on day zero); only
`fnd-1` (the broken promise) shows non-1.0 recency. This is the simplest rule that
reproduces every published number exactly.

**Alternatives considered**: Storing `state` directly on the fixture — rejected,
contradicts the DDL's own comment about which column the scoring engine, not the
fixture, is responsible for; would also silently diverge from real (future,
reader-produced) findings, which will never arrive pre-labeled with a state either.

## Decision: `finding_issue_map.rank_within_issue` is computed by `IssueGrouper`, not the fixture

**Decision**: The fixture supplies `(finding_id, issue_id)` pairs only — which findings
belong to which issue, matching `examples/01` §9's two issues exactly. `rank_within_
issue` is computed fresh on every `RecomputeScoreUseCase` run by `IssueGrouper`: within
each `issue_id` group, sort findings by *raw* points (before the rank factor itself)
descending, assign 1, 2, 3…, and upsert the result back into `finding_issue_map`.

**Rationale**: `data-base/05-schema-reasoning.md`'s own Notes section states this
explicitly: "`finding_issue_map.rank_within_issue` is assigned by the scoring engine at
scoring time (largest points first), not by the reader — readers never rank
(REQ-M5-P1)." This is exactly the load-bearing distinction `spec.md`'s scope boundary
already draws ("issue groupings are fixture data; rank-within-issue arithmetic is not")
— confirmed at the schema-comment level, not just inferred from the spec's own framing.

## Decision: a JSON fixture + Python script, not a static SQL file

**Decision**: `demo/fixtures/score-engine-findings.json` (9 findings' static
attributes — `reader_type`, `finding_type`, `magnitude`, `confidence`, a stakeholder/
product-area key, and which *citation strategy* to use — plus the 2 issues' groupings,
matching `examples/01` §9's `fnd-1`..`fnd-9` exactly), applied by a new
`scripts/seed_score_fixture.py`. Not a static SQL file (unlike `data-base/11-seed-
data.sql`) and not `scripts/seed.py`'s asyncpg-simple-query-protocol pattern either —
`cited_event_ids` must be resolved against real, already-inserted `events` rows at
seed time (UUIDs generated by `gen_random_uuid()` at insert, not knowable in advance),
so this script needs the same real, parameterized async DB access
`scripts/run_collector.py` already uses (SQLAlchemy sessions, the real
`EventRepositoryPort`/`DetectAbsenceUseCase`), not a one-shot static script.

**Rationale**: A JSON-fixture-plus-Python-script is exactly `SimulatedCollector`'s
precedent (feature 003) for the same underlying reason — the fixture's *shape* is
static and reviewable, but producing real, valid rows from it requires runtime
database work a flat SQL file can't do (dynamic UUID resolution, calling
`DetectAbsenceUseCase` for one citation, `AppendEventUseCase` for another).
`data-base/11-seed-data.sql` represents *real* deployment-shape data (Meridian's
actual client profile, sources, finding-type config) that every deployment would
plausibly seed via a simple static script; this feature's fixture is explicitly
synthetic proof data (`spec.md`'s own framing: "hand-authored... not real reader
output") needing real runtime resolution — conflating the two would also make a real
deployment's simple bootstrap script need this fixture's extra complexity for no
reason. Mirrors `demo/fixtures/meridian-week.json`'s precedent directly: the
demo/proof fixture stays a clearly separate artifact, in the same `demo/fixtures/`
location, from the real seed data.

## Decision: the full cross-module golden-replay test stays skipped; reconciliation and monotonicity get built for real

**Decision**: `tests/golden_replay/test_placeholder.py::test_golden_replay_reproduces_
dashboard_exactly` remains `@pytest.mark.skip` after this feature — its own
documented procedure (`tests/strategy.md` §Golden-replay tests) requires feeding
`demo/fixtures/meridian-week.json` through readers to produce findings automatically,
then through the Narrator for `narrator_outputs` — neither exists until features
005/008. `tests/scoring/test_reconciliation.py` and `test_monotonicity.py` **do** get
filled in for real by this feature — both operate on `findings`/`score_runs`/
`score_contributions` directly, which this feature owns completely, with no dependency
on readers or narrator.

**Rationale**: `tests/strategy.md`'s own table already scopes reconciliation and
monotonicity to `tests/scoring/` specifically (this module), separately from
golden-replay's broader `tests/golden_replay/` scope spanning the whole pipeline.
Attempting the full golden-replay test now would mean either building throwaway
reader/narrator stubs (speculative generality, P10) or leaving it half-implemented —
worse than an honestly-skipped placeholder with an accurate reason. This feature does,
however, deliver its own scoped determinism guarantee (`spec.md` SC-006: replaying an
identical ledger/profile/weight/damping state twice yields an identical score) via
`test_worked_example.py` calling `RecomputeScoreUseCase` twice against the same fixture
state and asserting byte-identical `score_contributions`.

## Decision: `RecomputeScoreUseCase`'s three real triggers, wired where their natural home already exists

**Decision**: `scripts/compute_score.py` (`trigger=manual`, mirroring `scripts/
run_collector.py`'s pattern exactly); `worker.py`'s existing APScheduler heartbeat gains
a second registered job calling `RecomputeScoreUseCase` (`trigger=hourly_heartbeat`),
alongside feature 003's absence-collector job; `SubmitProfileUseCase`
(`backend/app/context/application/use_cases.py`, feature 003) calls
`RecomputeScoreUseCase` after `ReplayUseCase.execute()` completes
(`trigger=profile_edit_replay`).

**Rationale**: All three already have a real, existing caller site from feature 003 —
no new orchestration mechanism needed, just one more call at each of three
already-established extension points. Matches `spec.md`'s own framing of these as the
three triggers "with a real caller" this feature wires, versus the four that need a
live reader pipeline or a weight-editing UI that don't exist yet.

## Decision: three new scoring-scoped ports, not a cross-module import of feature 003's adapters

**Decision**: `ClientProfileMultipliersPort` (stakeholder `influence_multiplier` /
product-area `criticality_multiplier` / `contract_value_band` / `renewal_date` lookups
against the current profile version), `DampingRepositoryPort` (`damping_weights`
lookups by `pattern_signature`), and `CoverageCheckPort` (`coverage_reports.sources_
read < sources_expected` for the freeze check, FR-011) are new ports defined in
`scoring/application/ports.py`, each with a `SqlAlchemy*` adapter in `scoring/adapters/`
querying the same underlying tables feature 003's `ClientProfileContextPort`/
`CollectorRunRepositoryPort` already query, but shaped for scoring's own needs
(multipliers, not calendar/exclusions; coverage existence check, not full report
construction).

**Rationale**: Constitution P8's Dependency Rule forbids `scoring.application`
depending on `context.adapters` or `ingestion.adapters` directly (a cross-module
adapter import would violate `.importlinter`'s `global-dependency-rule` contract, which
checks each module's own `domain`/`application`/`adapters` layering, not whether one
module's adapters happens to import another's). Two modules independently querying the
same table for different shapes is normal and expected in this architecture — feature
003 already set this precedent (`ingestion`'s `ClientProfileContextPort` and
`context`'s `ClientProfileRepositoryPort` both read `client_profile_versions`, for
different purposes).

## Decision: fixture findings cite real ledger event IDs, resolved at seed time — not fabricated UUIDs

**Decision**: `scripts/seed_score_fixture.py` resolves each finding's `cited_event_ids`
by querying the *real* `events` table (feature 003's ledger, already populated by
`scripts/run_collector.py` against `demo/fixtures/meridian-week.json`) rather than
hardcoding UUIDs — impossible anyway, since `events.id` is a fresh
`gen_random_uuid()` per row, not deterministic. Six of the nine findings cite the six
real MVP-source events directly: `fnd-1`/`fnd-2` → the `#456` `ticket_state_change`
event; `fnd-3` → the `tracking_api` `usage_measurement` event; `fnd-6`/`fnd-7` → Ana's
first Gmail `message` event; `fnd-9` → the `#398`-resolved `ticket_state_change` event.
`fnd-4`/`fnd-5` (Diego's absence/relationship) cite a real `absence`-type event — the
script calls `DetectAbsenceUseCase.execute()` (feature 003, already built) directly to
guarantee one exists, rather than depending on the worker's hourly heartbeat having
already fired. `fnd-8` (Ana's CSAT drop) is the one case with no real collector at all
— CSAT is a Post-MVP source (`decisions/01-mvp-scope-and-phasing.md`) with no adapter
built yet — so the script inserts one `survey_response`-type event directly via
`AppendEventUseCase` (feature 003's real, hash-chained append path, not a bypass),
documented in `demo/fixtures/score-engine-findings.json`'s own comment field as
representing a source with no live collector yet, matching `examples/01`'s own
framing of itself as a "full strength, all five sources" illustration rather than a
literal Phase 1 MVP trace.

**Rationale**: `findings.cited_event_ids` has no `REFERENCES` constraint (just a
non-empty `CHECK`), so nothing at the database layer *requires* real citations — but
P1 ("every claim links to the actual event that produced it") is a product principle,
not just a schema constraint, and this feature's own `spec.md` frames itself as proof
that hand-written findings can be checked by hand against real evidence. Citing
fabricated UUIDs floating disconnected from the ledger would quietly violate the
spirit of the one principle this feature exists to demonstrate, for the sake of
avoiding one extra synthetic event insertion. Six of nine needing zero extra work
(they already exist for real) and a seventh being free (the absence detector already
does exactly this) makes the honest path cheap enough that the one remaining
synthetic insertion (CSAT) is worth doing properly rather than cutting the corner
everywhere.

**Alternatives considered**: Dropping `fnd-4`/`fnd-5`/`fnd-8` entirely and scoring only
the six MVP-source-derivable findings — rejected because it would silently produce a
different score/band than the one number this feature's whole point is to reproduce
(`spec.md`'s acceptance criteria cite the full 9-finding total — see the correction
below for the exact current values); fabricating all nine citations as disconnected
UUIDs — rejected per the rationale above.

## Decision: `examples/01` §9.2's Issue A rank order is corrected, not reproduced literally

**Found during `/speckit-analyze`, not at design time.** `examples/01-end-to-end-
walkthrough.md` §9.2 and `data-base/05-schema-reasoning.md`'s own example rows publish
`fnd-2` at `rank_within_issue = 2` and `fnd-3` at `3` — but `fnd-3`'s raw points
(`base × influence × criticality × confidence × magnitude` = 11.1375) exceed `fnd-2`'s
(8.10) under the exact rule both documents state ("ranked by how much raw weight each
carries"). The published order contradicts its own stated rule.

**Decision**: `IssueGrouper` implements the rule correctly and generally — no
fixture-specific exception, no hardcoded issue IDs — which ranks `fnd-3` 2nd and
`fnd-2` 3rd for this fixture, not the order `examples/01` §9.2 happens to publish.
This changes Issue A's total from the previously-assumed `47.87` to `48.60`, and
cascades to `total_negative_points = 68.04`, `total_points = 64.04`, `score ≈ 85.64`
(band unaffected — still `at_risk`). `spec.md`, `data-model.md`, `quickstart.md`, and
`tasks.md` all cite these corrected numbers as of this decision.

**Rationale**: An `IssueGrouper` that special-cased one issue's rank order to match a
specific fixture would be unbuildable without a hardcoded exception — directly
contradicting P10 (no special-casing) and invalidating `test_reconciliation.py`/
`test_monotonicity.py`'s premise, both of which require one general algorithm to hold
correctly for *arbitrarily generated* issue groupings, not just this feature's own
fixture. `examples/01`'s published numbers are the thing with the error here, not this
feature's arithmetic — fixing this feature's own artifacts to match the correct,
general rule is the sound response; silently reproducing an inconsistency to match a
source document that contradicts itself is not. `examples/01` itself is unaffected by
this feature's scope; correcting that document is a separate, later concern.

## Note: a naming drift observed, not a blocker

The constitution (P9) references `backend/app/ledger/` as one of the two modules whose
changes require a passing golden-replay run before merge. No such directory exists or
is planned — `decisions/02-repo-and-tooling.md`'s module map (feature 001, before
`architecture/09`'s later three-ring update) already assigned the ledger (M2) to share
`backend/app/ingestion/` with the collectors (M1), and feature 003 built exactly that,
verified working. This looks like the constitution retaining an earlier, informal name
for the ledger concern rather than a real second module. Flagged per the constitution's
own Governance clause ("if a requirement, this constitution, or any architecture
document ever seem to disagree... that is a bug to fix, not a judgment call to make
silently") rather than silently resolved — this plan proceeds using the real, existing
`backend/app/ingestion/` path, and treats the constitution's `backend/app/ledger/`
reference as meaning the same thing until a future constitution amendment corrects the
wording.
