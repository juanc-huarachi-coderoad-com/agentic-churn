# Phase 0 Research: Ask Agent Flexible Response Formats

Both `NEEDS CLARIFICATION` markers from spec.md were resolved during `/speckit-specify` (genuine LLM-generated Markdown, mechanically fact-checked; a single reply may contain multiple ordered parts). What follows are the technical decisions needed to implement that resolution against the actual current codebase.

## Decision 1: `response_mode` is a same-call, schema-constrained field on `ClassifyOutput` — not a new LLM call, not a new port

**Decision**: Extend `ask_agent_graph.py`'s `ClassifyOutput` dataclass with a third field, `response_mode: ResponseMode` (`StrEnum`: `component_only | text_only | hybrid`), decided by the same `classify_intent` call that already decides `intent`/`subject_hint`. `LLMPort.generate_structured(prompt, schema)`'s signature is untouched — this is a richer schema passed to the same method, not a port change.

**Rationale**: `LLMPort` is shared across all 6 LLM touchpoints (readers, Narrator, Ask agent classify, Draft composer); changing its signature would ripple everywhere. The research done during `/speckit-plan` confirmed the port already supports "any Pydantic/dataclass schema" — the constraint is what schema is designed, not the interface. Deciding response format in the same call that decides intent keeps this a single classification decision, not two.

**Alternatives considered**:
- A separate LLM call just to decide response format — rejected: doubles classification cost and latency for a decision that's naturally part of the same "what is this question asking for" judgment.
- Let the frontend/router decide response format heuristically from the matched intent (e.g. always hybrid for `top_risk`) — rejected: this is exactly the kind of judgment the model is positioned to make from the question's actual phrasing ("what's driving this?" vs. "show me the risk drivers"), and a hardcoded per-intent mapping would defeat the point of the feature (US1's whole premise is that phrasing, not just topic, determines whether prose is warranted).

## Decision 2: `response_mode` reuses the existing 8 intents and 3 tools — no new "conversational" intent, no new grounding mechanism

**Decision**: Text/hybrid responses are only ever generated for a question that already matches one of the 8 existing structured intents (`score_delta`, `baseline_check`, `quiet_stakeholders`, `top_risk`, `recommended_actions`, `commitments_status`, `timeline`, `write_to_stakeholder`) — `resolve_and_render`'s existing tool-fetch logic for that intent runs exactly as it does today, unchanged; `response_mode` only changes what's *done* with that already-fetched data (render it as a component, write prose about it, or both). A question that matches none of the 8 intents (`Intent.NONE`) still routes to the unchanged `fallback` node — this feature does not add a new "the assistant can answer anything conversationally" capability, only a new *presentation* of an already-answerable question's answer.

**Rationale**: Directly satisfies FR-012 ("decline/fallback behavior unchanged — this feature only extends how an *answerable* question can be answered") without inventing a new answerability heuristic, which would be a real, unbounded scope expansion and a genuine new risk surface (an "I can answer anything" mode with no data backing it). Spec.md's own US1 example — "why does this matter for renewal?" — is a real question that plausibly classifies to `top_risk` or `recommended_actions` with `response_mode: text_only`: same data-fetch, prose instead of (or alongside) the component. This keeps the "no new facts" guarantee (Rule 4) load-bearing on the exact same data-fetch code that already exists and is already trusted.

**Alternatives considered**:
- Add a new, broader "conversational" intent value with looser grounding (e.g. always fetch the narrator summary + coverage state regardless of question) — rejected: this is a real scope expansion beyond what spec.md asked for (SC-001 says "the same categories of question that are declined today purely for lacking a matching component," not "any question at all"), and it would mean the assistant's answerable surface silently grows in a way `/speckit-clarify`'s own resolution didn't authorize.

## Decision 3 (revised during implementation): A hard, enforced, live-tested cap on the text-generation call

**Original decision**: an 8s "no retry" budget for `text_only`/`hybrid` responses, matching readers' 8s single-call budget.

**Why it needed revision**: `LLMPort`'s shared `AnthropicLLMAdapter` implementation has its own internal 3-attempt retry (8s-per-attempt timeout, 1s/2s backoff) baked in for *every* caller — including the Ask agent's classify call, which the original constitution text describes as "2.5s, no retry" but which, at the code level, was never actually capped that way; it just usually finished fast. This feature's second call inherits the same shared behavior. Without an explicit outer timeout, live-testing the real implementation against the real model during this feature's own build produced a genuine **72-second** response for a `text_only` question and an **81-second** one for `hybrid` — both roughly 9-10x the originally-documented budget. This was found by actually running the feature end-to-end against a live model and real seeded data, not assumed.

**Revised decision**: `generate_text`'s call to `llm.generate_structured` is wrapped in `asyncio.wait_for(..., timeout=15.0)` — a hard ceiling enforced in code, not just described in a docstring or architecture doc. 15s was itself tuned empirically: an initial 8s cap was live-tested and consistently too tight to let a real generation finish at all (every attempt got cut off); the real fix that mattered was tightening `_text_generation_prompt` to explicitly ask for a short, 2-4 sentence answer (better chat UX on its own merits, and also faster to generate) — after that change, real generation typically completed in ~7-8s, making 15s genuine tail-latency headroom rather than a number picked to make failures rare by brute force. `component_only` responses are untouched — they still go through only the pre-existing classify call, whose own timeout/retry behavior this feature does not change.

**Rationale**: A feature whose own safety story depends on "the CS manager always gets a real, timely answer" cannot rely on an unenforced, documentation-only budget when the shared adapter it calls through has its own, different, uncoordinated retry policy already baked in. Enforcing the cap for the one new call this feature adds (rather than trying to change the shared adapter, which would affect five other LLM touchpoints far outside this feature's scope) is the smallest change that makes the documented guarantee actually true.

**Alternatives considered**:
- Leave the 8s number in the documentation uncorrected, treating the 72s/81s live results as a fluke — rejected: it reproduced consistently across multiple live runs at 8s, not once; shipping a known-wrong number in the constitution/architecture docs would be exactly the kind of "aspirational, not mechanical" gap this project's own AI-safety culture (Rule 4's "mechanical, not aspirational" framing) explicitly warns against elsewhere.
- Fix the shared `AnthropicLLMAdapter` to accept a per-caller timeout/retry override — rejected as out of scope: it's used by Tone/Intent/Meeting readers, Narrator, and Draft composer too; changing it is a cross-cutting change this feature didn't set out to make and shouldn't make as an unplanned side effect.
- Retry the text-generation call once, like readers do — rejected: at up to 15s already, a retry could push a chat response well past what's tolerable in a synchronous "waiting for a reply" UI; the existing Ask agent design deliberately avoids retries for exactly this UX reason.
- Fail the entire response (fall back to the generic "taking longer than expected" message) if text generation fails, discarding the already-fetched `component_props` — rejected: wasteful and a worse experience than the graceful component_only degradation, which reuses data that was already successfully fetched.

## Decision 4: Fact-check reuses `app.narrator.domain.services.fact_check`/`VerifiedFactSet` directly — no new fact-checking logic

**Decision**: The new text-generation step's fact-check imports `fact_check(sentence, facts)` and `VerifiedFactSet` from `app.narrator.domain.services`/`app.narrator.domain.entities` directly (a domain-to-domain import, explicitly allowed by constitution P8). A `VerifiedFactSet` is built the same way the Narrator already builds one — from the numbers/names extractable in the same tool-fetched data (`component_props`) already used to render the component for that intent — plus the same "every point value is itself a real, citable number" extension the Narrator's own `_build_verified_facts` already applies. Generated Markdown is fact-checked **per sentence outside fenced code blocks** (mirroring the granularity the Narrator already applies per-reason/per-action, not an all-or-nothing check on the whole response) — any sentence that fails is dropped from the response entirely, never rewritten (FR-005). Content inside a fenced code block is never fact-checked (a code snippet is literal text, not a factual claim about the account).

**Rationale**: This is the single most load-bearing decision in this feature and the one place reinventing something instead of reusing it would be the real risk. The Narrator's `fact_check()` is already a tested, working, precedented mechanism for exactly this problem (drop, never rephrase; fails closed on ambiguous extraction). Per-sentence granularity (not whole-response) matches how the Narrator already handles its own multi-item outputs (`reasons`, `actions` — each independently checked and independently droppable) rather than introducing a new, coarser granularity for this feature alone.

**Alternatives considered**:
- Write a new, Ask-agent-specific fact-checker — rejected outright: duplicates working, tested logic for no functional gain, and creates two independently-maintained implementations of the same safety-critical check (a violation of P10/YAGNI, and a real maintenance/consistency risk for a mechanism this safety-critical).
- Fact-check the whole Markdown blob as one unit (drop the entire response on any single failing claim) — rejected: far more destructive than necessary; a response with one unverifiable aside shouldn't lose an otherwise-correct paragraph, and per-sentence dropping is the Narrator's own established behavior already.

**Addendum found during implementation — raw internal identifiers aren't caught by `fact_check` alone**: live-testing surfaced a real generated sentence that quoted a raw `score_contribution_id` UUID verbatim (e.g. `` `12a26b95-c7ca-4df1-a80a-e17972584de6` ``). This technically *passes* `fact_check` — the UUID demonstrably exists in the source data, which is exactly what "verified" means — but a raw internal identifier is never something a CS manager should see in prose. `fact_check`'s number/name extraction patterns don't match a UUID's shape at all, so it was never being checked either way. Two fixes, both applied: (1) `_text_generation_prompt` now explicitly asks the model not to quote any `*_id` field or UUID, referring to what it identifies in plain words instead; (2) a mechanical backstop, `_UUID_PATTERN`, drops any sentence containing a UUID-shaped token regardless of what `fact_check` says — the same "fails closed on the display side" philosophy Rule 4 already establishes, applied to a claim-shape `fact_check` was never designed to catch.

## Decision 5: The answered response becomes an ordered `parts` list; decline/fallback is untouched

**Decision**: `AskAgentResult` (and the API's `AskComponentResponse`) is replaced, for the *answered* case only, by a `parts: tuple[ResponsePart, ...]` field, where `ResponsePart` is `TextPart(markdown: str) | ComponentPart(component: str, component_props: dict)` (new value objects appended to the existing `app/experience/domain/entities.py`, which already holds dashboard/evidence/draft-composer entities and already imports `FactCheckResult` from `app.narrator.domain.entities`). For `response_mode: component_only` (unchanged default), `parts` is always exactly `[ComponentPart(...)]` carrying the identical `component`/`component_props` data the route returns today — `AskComponentResponse`'s old flat shape is fully reconstructable from `parts[0]` for any existing consumer, satisfying SC-002's zero-regression requirement precisely. `AskFallbackResponse` (decline/fallback) is **not** touched by this change at all — it keeps its existing flat `fallback_text`/`sources`/`declined_reason` shape, per FR-012.

**Rationale**: A single, uniform `parts` list is the simplest shape that can represent all three answered modes (component-only = 1 part, text-only = 1 part, hybrid = 2+ parts) without a mode-specific branch in the API contract itself. Keeping `AskFallbackResponse` completely separate (rather than unifying everything, including declines, into `parts`) preserves the meaningful distinction FR-012 asks for: a decline is a hand-authored, non-fact-checked static string, never LLM prose — collapsing it into the same `TextPart` shape as genuine generated Markdown would blur exactly the boundary this feature's own safety story depends on.

**Alternatives considered**:
- Unify everything (component, text, hybrid, *and* decline/fallback) into one `parts`-based response — rejected: would make a hand-authored decline string indistinguishable, at the type level, from fact-checked generated prose, undermining the very distinction Rule 4 exists to preserve.
- Keep `AskComponentResponse`'s old flat shape and bolt on an *optional* separate `markdown` field alongside it — rejected: cannot represent an ordered hybrid response (e.g. text, then component, then more text) required by FR-009; a single optional field can express at most one text block in a fixed position, not an arbitrary ordering.

## Decision 6: `ask_queries.response_mode` — one new, nullable column

**Decision**: Add `response_mode` (`text`, nullable) to `ask_queries` via one additive Alembic migration. Populated with `component_only`/`text_only`/`hybrid` for answered queries; left `NULL` for decline/fallback rows — mirroring the existing convention where `rendered_component` is already `NULL` for fallback rows today.

**Rationale**: FR-013 requires no format-specific gap in logging; without this column, the existing `rendered_component`/`declined_reason` fields alone can't distinguish a `text_only` answer (no component) from a genuine decline (both currently look like "no component" in the log). Nullable + additive is the schema-discipline convention this codebase already follows for lightweight, analytics-oriented columns.

**Alternatives considered**:
- Infer `response_mode` after the fact from whether `rendered_component`/a hypothetical text field is populated — rejected: fragile (requires every future reader of this table to re-derive the same logic) and less honest than just recording the decision that was actually made, matching this codebase's general "record the real decision, don't make readers reconstruct it" convention (e.g. `matched_intent` is recorded directly rather than inferred from `declined_reason`'s absence).

## Decision 7: Frontend Markdown rendering — `react-markdown`, no raw-HTML plugin

**Decision**: Add `react-markdown` (no `rehype-raw`/`rehype-sanitize` plugin) as the one new frontend dependency. It compiles Markdown directly to React elements and never renders raw embedded HTML by default — a real, structural prompt-injection defense at the rendering layer (client message content that made it into generated Markdown, even if it contained something like an HTML `<script>` tag, is rendered as inert literal text, never executed), consistent with FR-007 and constitution AI-safety Rule 2. Fenced code blocks render via its default `<pre><code>` output with monospace styling — no separate syntax-highlighting library, per Decision 8.

**Rationale**: `react-markdown` is the de facto standard React Markdown renderer — small, actively maintained, and its default (no raw-HTML plugin installed) is exactly the safe posture this feature needs without any extra configuration to get wrong. Confirmed via `frontend/package.json` inspection that no Markdown library exists today, so this is a genuinely new dependency requiring justification (constitution's Full-Stack Engineering §2 "UI & Styling" rule requires approval for anything beyond the named stack) — approved here as the minimal library that satisfies FR-001's "correctly formatted text, including distinguishable code blocks" without introducing an HTML-injection surface.

**Alternatives considered**:
- Hand-roll a minimal Markdown-to-JSX converter — rejected: reinvents a well-solved, security-sensitive parsing problem (Markdown parsing edge cases are a real source of XSS-adjacent bugs) for a one-library dependency that already solves it safely by default.
- `dangerouslySetInnerHTML` with a Markdown-to-HTML string library (e.g. `marked`) plus a sanitizer — rejected: two dependencies instead of one, and re-introduces exactly the raw-HTML-rendering surface `react-markdown`'s default avoids entirely; strictly worse on the one axis (prompt-injection safety) this feature cares most about.

## Decision 8: No syntax-highlighting library

**Decision**: Code blocks render as plain, monospace, non-reflowed text (react-markdown's default) — no syntax-highlighting dependency (e.g. `shiki`, `prismjs`) is added.

**Rationale**: FR-001 requires code snippets to render in "a distinguishable, non-reflowed format" — a plain `<pre><code>` block already satisfies this exactly. A syntax highlighter is real added bundle weight and a second dependency for a capability the spec doesn't ask for (per P10/YAGNI); this is a customer-success churn tool, not a developer tool, so heavy code-authoring UX is out of proportion to the actual use case.

**Alternatives considered**: A syntax highlighter — rejected per P10; can be added later as a scoped follow-up if real usage shows a need, not speculatively now.
